## Approval and authorization gate

Approval is conditional on existing tenant, organisation, resource and classification boundaries. It does not authorize modifying API response semantics or substituting validation history for current access policy.

- Organisation: `src/bri/api/app.py:846–875` first authorizes individual nodes and then filters relationship endpoints to the visible set; the node detail independently checks parent authorization. `src/bri/access/policy.py:35–48` matches the exact tenant, action and node with no traversal or inheritance. The API rejects multi-tenant principals before scoped access.

## Isolated implementation

Migration `0021_user_permission_delegation.sql` removes runtime writes to shared role definitions and native assignments. It preserves forced RLS, pins registered singleton bundles to their sole approved permission, and disallows reusing them in legacy synthetic assignments. Catalog records and delegation authority are provisioned only by the platform database boundary. No bundle or authority is seeded. The restricted synthetic data seeder only verifies the pre-provisioned role catalog; the disposable verifier alone bootstraps its fixture catalog as the test database administrator.

Authority is an explicit tuple of tenant, Admin, exact node and permission; holding a read grant does not confer that authority. A native assignment created by this workflow adds only the checked singleton permission at the selected node. The private version and ownership record prevent stale updates and reversal of assignments managed elsewhere. The mutation rechecks the actor, target, session and freshness under existing governance, role and session locks. The assignment, immutable audit and A10 invalidation of affected sessions commit together. No membership or administrator roster changes are performed.

The staged GET and PATCH operate on one account, node and approved permission. Versions cross the HTTP boundary as decimal strings. The normal API denies the routes without authentication, request parsing or database work; the hosted proxy cannot forward them and the normal UI shows a disabled notice. The migration does not grant execution of either delegation routine to the runtime login. The disposable test fixture checks that default ACL before activating the routines in its private cluster. The staged app uses an owner-only Unix socket and an injected provider verification fixture, not a live provider or hosted database.

Delegated `knowledge:read` supplies only the exact-node check of the P1 reader; independent policy for the record and version must still allow each publication. Revocation invalidates A10 sessions atomically but does not recall content already delivered. A pre-existing grant through another platform-managed role is not a delegation grant and cannot be revoked here. To retire authority, first revoke any outstanding delegated assignments that need removal, then remove the authority rows; removing authority alone does not revoke previously assigned reads. Suspension blocks access and invalidates sessions but does not erase assignments, so reactivation can restore an existing delegation. The staged workflow does not revoke grants for ineligible targets. Before any hosted enablement, define how those grants are retired, bind database execution to the verified actor path, and harden staged UI confirmation against changing transport or node-catalog context.
