## Existing disclosure surface

| Candidate | API and workspace entry points | Effective disclosure |
|---|---|---|
| `organisation:read` | `GET /v1/organizations/structure`, `GET /v1/organizations/nodes/{node_id}`; workspace dashboard and Organisation screen through the same-origin proxy | Exact-node ID, type and display name. Parent ID is suppressed unless the parent is separately authorized. The structure endpoint also combines the recipient's visible nodes: where both endpoints are visible it discloses relationship ID, endpoints, type and the `grants_access` flag. That flag is returned as data; these readers do not use it to grant access. Granting one node can therefore newly expose links to nodes the recipient already reads. |
| `knowledge:read` | `GET /v1/knowledge`, `GET /v1/knowledge/{record_id}`, `GET /v1/knowledge/search?q=…`, `GET /v1/sources/{record_id}`; dashboard, Knowledge list/search/detail and Source details through the same-origin proxy | Exact-scope validated knowledge. List and detail include the full stored extraction text, title, record/scope IDs and validation state, plus source/version and extraction IDs, version label, SHA-256, extractor name/version and stored source location. Local lexical search can return a verbatim answer and cited excerpts with provenance; it does not call an AI model. The source route projects provenance for the same validated records, not an original-file download. The database list has no latest-version filter: previously validated versions can be visible if still present in the validated set. |

## Approval and authorization gate

The owner approved the disclosures above, including jointly visible relationships and older validated versions only if currently authorized. Approval is conditional on existing tenant, organisation, resource and classification boundaries. It does not authorize modifying API response semantics or substituting validation history for current access policy.

- Organisation: `src/bri/api/app.py:846–875` first authorizes individual nodes and then filters relationship endpoints to the visible set; the node detail independently checks parent authorization. `src/bri/access/policy.py:35–48` matches the exact tenant, action and node with no traversal or inheritance. The API rejects multi-tenant principals before scoped access.
- Knowledge: `src/bri/api/app.py:410–430` filters by tenant, exact node and membership in `validated_knowledge`. `Resource` in `src/bri/access/policy.py:29–32` models tenant and node, not a record or version authorization decision. `db/migrations/0004_knowledge_lifecycle.sql` records provenance and approval; it has no current resource/version classification or restricted/withdrawn state enforced by the read path. Removing node access denies every version at that node, but retaining node access does not let the system exclude a previously validated version that is no longer permitted under a finer-grained policy. The target classification and lifecycle controls in `architecture/knowledge-architecture.md` are not implemented in this serving path.
- Source references: `src/bri/api/app.py:1127–1142` uses the same loader, so provenance has no separate authorization bypass, but inherits the missing resource/version check. The route returns metadata, not original-file access; the workspace displays the location as text. Search uses local lexical matching in `src/bri/knowledge/query.py`, not a model call.

Resume only once current resource/version authorization can be evaluated consistently for list, detail, search and provenance, including denial of historical content when it is no longer authorized even if node access remains. Eleven existing focused tests passed: they exercise current organisation and knowledge behavior, not the missing classification/version boundary or A11.4 delegation.

The approved envelope is one explicitly authorized client Admin with fresh provider-verified TOTP, same-tenant active User/SuperUser targets only, exact-node and platform-maintained allowlist, no self-grants, no membership-class or role-definition changes, and no hosted write path. Before adding any delegation mutation, constrain legacy direct catalog writes and indirect changes, including role-FK cascades and alternate paths. Protect allowlisted bundles and verify each resulting effective permission under the existing role ceiling; possession of an action is not authority to delegate it. Keep forced RLS, the two-eligible-admin minimum, version checks, immutable audit and A10 session invalidation. No implementation or catalog changes were made for this assessment.
