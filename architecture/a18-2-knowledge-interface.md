# A18.2 — local synthetic Knowledge Interface

## Workspace and trust boundary

The dedicated Knowledge Interface is `/knowledge/search`, linked from the local fixture navigation. The existing A13 `/knowledge`, A15 `/reports`, and A16 XLSX interfaces remain distinct. No release or hosted route is added. The development-only numeric loopback workspace uses its existing server-side native signed-session cookie verification. The browser does not supply tenant, principal, permission or publication authority.

`GET /v1/knowledge/search/scopes` (0036) supplies version 1 `complete` with `scopes: [{scope_node_id, display_label}]`, including an empty array when the current verified native session has no eligible scopes. It returns a 503 versioned `unavailable` with no entries if the operation cannot complete. Only nodes with current effective exact-node `knowledge:read` are eligible. Record, version and publication availability do not influence the discovery projection. Labels are authoritative, tenant-qualified and ordered by label and then node ID under PostgreSQL C collation. Duplicate labels remain distinct. Eligible scope limits are 500 entries and 131,072 UTF-8 response bytes, with no partial response or pagination. The native identity lookup has a separate one-second SQL deadline; the protected operation has its existing five-second deadline and 16 MiB temporary-file ceiling. 0036 adds no role, table, index, policy or public execution; the named reader execution is fixture-only.

The local bridge forwards only the explicitly allowed methods and paths. A fresh request checks the cookie again. The opaque bridge context binds requests to the session that supplied the choices and detects a changed browser cookie on the next request; it does not authorize any read. There is no protected storage or cache. Inactive tabs and abandoned pages discard the in-memory scope, search and evidence state; initialization, return to the tab and explicit refresh check discovery again. A session change that happens without an observable browser event is detected on the next protected request or refresh. Already delivered information cannot be recalled from an idle browser. No claim is made about all browser history or BFCache behavior.

## Search and follow-through

The selector offers only discovered node identifiers and labels. Searching is explicit and literal; each request sends the exact selected node and a query within the existing normalized UTF-8 byte limit. Contract version 1 of `POST /v1/knowledge/search` is decoded as one receipt, with no partial rendering if a hit is invalid. The view preserves returned ordering and renders source IDs, excerpts, line spans, worksheet titles and cells as text. The UI does not invent a filename or match count. Excerpt clipping is marked and provenance includes the format-appropriate digests and XLSX processing versions.

CSV evidence uses the fixed `/v1/knowledge/csv/{record_id}/versions/{version_id}/evidence` template. The receipt does not contain source bytes or an independent `source_id`; the accepted `csv:<exact UUID>` association is checked through the returned matching record/version and digests. The UI shows the receipt's recorded physical line span and separately identifies the matched line span. XLSX uses the fixed `/v2/knowledge/xlsx/{record_id}/evidence/{version_id}` template, strict v2 provenance and the accepted worksheet constraints. Pagination is explicit and never downloads all pages automatically. No response-provided URL is used as an arbitrary navigation target. Existing A16 v1 remains unchanged.

New search, query or scope transitions, refresh, and authorization failures retire prior requests, clear protected findings, and suppress late completions through request ownership as well as abort. Evidence denial clears prior search and evidence without distinguishing missing, wrong or inaccessible versions. A fresh authorized search is required. Complete-empty, unavailable, authorization denied and initial states are distinct; no cached or partial result is shown as complete.
