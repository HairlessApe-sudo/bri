# A10: controlled re-enrollment after an MFA reset

**Hosted status: blocked.** A completed reset is evidence of removal, not evidence of who now holds a usable replacement. There is no hosted listener, enrollment URL, automatic login, role bootstrap, signer or provider integration in this change. The local receiver demonstrates a contract; it does not establish that a provider supplies these facts.

## What actually releases the quarantine

1. On the first authorized `approval_work(...,'BEGIN',...)`, 0010 now reserves the 0008 `factor_reenrollment` operation **without changing principal status**. Reservation revokes existing sessions and blocks even unseen session IDs. An independent suspension prevents execution. A failed/ambiguous removal or `COMPLETED` alone leaves the operation pending. 0012 changes the precise legacy fragments under the migration transaction and aborts on an unexpected definition; it doesn't install a parallel copy of the removal worker.
2. After the committed removal, an isolated platform identity-proofing authority attests that the rightful account holder is bound to a specific replacement factor in a controlled ceremony. Its case ID is an immutable event ID. The independently provisioned provider authority must attest both the creation of that new TOTP after removal and a **successful challenge on that exact factor**, causally bound to the platform case and operation. Both attestations must name the same tenant, approval, pinned issuer, native subject and factor; none of the originally pinned IDs can be reused. The provider may deliver first, but cannot complete until redelivery after the platform case commits. Platform verification cannot clear a barrier.
3. The database takes the 0009 governance fence then the 0008 session guard at READ COMMITTED. It rechecks the reservation, completed removal, active undeleted ordinary principal, single-tenant membership and active native link. Both proofs must be recent (local proposal: 15 minutes), after removal and newer than the session cutoff and the 0011 latest observed provider change. A superseded case, clock ambiguity, rebind, suspension or pending deletion fails closed. Ordinary 0011 activity events never supply positive proof. A newly recorded deletion request also invalidates existing sessions; pending deletion denies session start.
4. The matching provider receipt, `confirmed_at`, fresh primary-auth cutoff, session revocation and immutable `auth.mfa.factor_enrolled` audit commit together. A restrictive policy also gates the older generic confirmer. Identical redelivery returns `duplicate` without any write; it is **not** a statement about current access. Substitution of event content is rejected. Re-entry still needs normal provider authentication, fresh primary evidence after the final cutoff, verified TOTP/AAL2, membership, session and resource authorization. Nothing here creates a session, restores a grant, or changes any principal to active.

**Existing 0010 suspensions:** there is no reliable reason code proving that such a suspension was *only* a reset. No backfill or automatic unsuspension is safe. These accounts stay blocked for separate governed adjudication; an old approval, elapsed time, or a matching factor is not an exception.

## Operator decisions required before any bootstrap

- Approve the platform's human identity proofing procedure, independent reviewers, how it binds the human to the native account and exact factor, and the out-of-band enrollment channel available during quarantine. The original reset voters, an ordinary session or a recovery email alone cannot vouch for identity. Never give a quarantined user ordinary application access to perform the ceremony.
- Obtain authoritative **provider-origin causality** for creation and verified TOTP challenge, including immutable event IDs, issuer/subject, factor ID, ceremony/case and approval/tenant association. Missing fields must not be reconstructed by looking up the user's outstanding case, matching timestamps or consulting a current factor inventory. A signed translation of weak evidence is still weak evidence. Require reliable clocks, replay handling and synchronous protection against undiscovered out-of-band changes. Without those guarantees leave both receivers unprovisioned.
- Approve the issuer pinned in 0011, role and key custody, freshness/order rules, source authentication and isolation. Two independent services, different protected high-entropy keys (at least 32 bytes), dedicated direct `NOINHERIT`, nonowner, nonprivileged logins `bri_reenrollment_platform` / `bri_reenrollment_provider`; no inherited or assumable roles. Audit effective, default and PUBLIC privileges. If approved, grant only database connect, `USAGE` on `bri` and `EXECUTE` on `bri.record_reenrollment_proof(text,uuid,text,uuid,uuid,uuid,uuid,timestamptz,timestamptz)`. No table privileges, generic confirmation, status updates or cross-service access. The ordinary app, browser, approval worker and 0011 ingest login receive neither grant nor key. Use protected transport and secrets management; rotate/disable each authority independently. Do not use an end-user-pool login and `SET ROLE`.
- The local adapter checks HMAC-SHA256 over exact bounded UTF-8 JSON bytes with a pinned per-authority, per-issuer key and checks the actual database login. Its two versioned assertion kinds are application contracts, **not provider event names**. Real signer services must verify the upstream facts before constructing an assertion; never expose a signing service that echoes caller fields. The proof store retains only scoped IDs and timestamps. Approve access, retention, key rotation and the escalation procedure for an expired/conflicting case or unclassifiable legacy suspension; no administrative override is included here.

## Isolated reproduction

From the repository root, with the approved local PG16 binaries already present:

```sh
env -i PATH=/usr/bin:/bin HOME="$TMPDIR" TMPDIR="$TMPDIR" PYTHONDONTWRITEBYTECODE=1 \
  PYTHON_DOTENV_DISABLED=1 PYTHONPATH=src:tests:. \
  BRI_TEST_PG_BIN="$TMPDIR/a10-approval-pgbin/pgserver/pginstall/bin" \
  .venv/bin/python -m unittest -v test_reenrollment test_reenrollment_pg
```

The fixture initializes and removes a private Unix-socket-only cluster, runs the checked-in migration runner and verifies ledger checksums and no-op replay. Test keys, proof bodies, actors and provider changes are synthetic. A successful test proves only this local contract, not a hosted proof source or deployment approval.
