# A10: private provider security event consumer

**Status: local ingestion is implemented; hosted use is blocked.** This consumer is not a subscription, an HTTP route, an Auth hook, a browser callback, or a signer. Nothing in 0011 enables a source by default. It reads and writes only BRI-owned objects. It does not perform a reset, delete a factor, decide an approval, or grant access.

## Input and acknowledgement

The future project-specific forwarder is a trust anchor. It must verify a provider-originated record on an authenticated server-only channel, bind the project and affected Auth user (not necessarily the actor), strip all other data, then authenticate the normalized envelope. Its key and the worker's DB identity must not be available to the web/API process. The signature below is a **BRI forwarder protocol**, not a signature Supabase promises to supply.

`ProviderEventConsumer(issuer, key, connect).consume(body, signature)` accepts UTF-8 JSON bytes (1–2048 bytes); `signature` is lowercase hexadecimal HMAC-SHA256 of the ASCII bytes `BRI.provider-security.v1`, one NUL byte, then the original body bytes. Use a separate random key of at least 32 bytes per environment/project. Compare before parsing or opening the DB. No bearer token, cookie or browser-provided correlation is evidence. Fields are mandatory, unique and exhaustive:

| Field | Contract |
|---|---|
| `issuer` | Exact pinned HTTPS Auth issuer ending in `/auth/v1`; independently pinned in the database. |
| `event_id` | Immutable source event UUID, canonical lowercase, non-nil. Never use a delivery ID, a fresh UUID on retry, or a hash of mutable metadata. |
| `subject` | Canonical non-nil UUID of the affected native Auth user. BRI resolves issuer + user + subject to the principal and derives tenant. Unmapped or ambiguous records are not accepted. |
| `action`, `outcome` | Allowlist below. Outcome is `success`, `failure`, `denied`, or `observed`. Use `observed` for an attempt with unknown outcome, never infer successful authentication or MFA. |
| `occurred_at` | Source UTC time `YYYY-MM-DDTHH:MM:SS[.ffffff]Z` (1–6 fractional digits if present). Future dates reject; delayed historical deliveries are allowed. Never use receipt or token-refresh time. |
| `operation_id` | Normally JSON `null`. Only a completed password change may carry the exact canonical UUID of a causally linked BRI reservation, authenticated independently by the forwarder. If that binding is unavailable send `null`; do not search for the latest pending request. |

| Accepted actions | Effect |
|---|---|
| `user_updated_password` | Completed credential change (`success` only); fence sessions. A password recovery **request** is not this event. |
| `factor_deleted`, `factor_unenrolled`, `factor_updated` | Completed change (`success` only); fence sessions and submit negative-only TOTP evidence for the affected admin identity. Never establish enrollment or verify TOTP. |
| `generate_recovery_codes`, `recovery_codes_deleted` | Completed change (`success` only); fence sessions. Do not transmit codes. |
| `login`, `logout`, `user_recovery_requested`, `user_reauthenticate_requested`, `factor_in_progress`, `challenge_created`, `verification_attempted`, `mfa_code_login` | Audit only. No session start, step-up, confirmation, or change to governance eligibility. |

Supabase's public **Auth Audit Logs → Log actions reference** documents these source actions and warns that logs may be delayed. Its example is not a signed subscription, proof of stable event identity, or a way to correlate a BRI operation. A complete deployment must account for additional factor types or change paths not unambiguously represented here; reject unrecognized messages rather than guessing their meaning.

`connect()` supplies a **fresh idle transactional psycopg connection** (READ COMMITTED, no autocommit) to the private restricted worker login. `applied` and `duplicate` acknowledge **commit**, not provider execution or regained access. On invalid signature/schema, missing subject, collision, timeout, serialization/DB error or ambiguous commit: no successful acknowledgement. Retain the original authenticated source record in a protected durable spool; retry transient failures unchanged with backoff, isolate permanent conflicts and alert. Never manufacture a replacement event ID. Do not log private payloads, passwords, tokens, factors, IPs, links or signing keys. A database failure is not evidence that the provider operation failed; never repeat an external mutation solely on that basis.

## Database and session contract

* 0011 uses the runner-owned transaction, after 0008–0010. It creates an empty singleton issuer registry and append-only forced-RLS receipts keyed by `(issuer,event_id)`. Identical normalized facts are a no-op; a reused key with different facts raises. One transaction inserts the receipt, audit and any invalidation/confirmation/negative observation. `auth.provider.<action>` is reserved from `bri_app`. The provider is not labeled a human actor. `request_id` joins the audit and per-session revocations to the receipt's internal `correlation` UUID; source time and receipt time are distinct.
* 0008's `lock_session_guard` serializes event application with `start_security_session`. `invalidate_security_sessions` revokes materialized sessions of the principal, appends revocation audit and advances the durable `primary_after` cutoff. Even a previously unseen session ID needs immutable primary authentication **after** the cutoff; refresh `iat` cannot restart it. A strictly older provider change is audited but cannot rewind the provider-time high-water mark, revoke newer sessions again, or confirm a reservation. Distinct changes with the same time conservatively fence again. A new high-water change may also revoke sessions opened between its occurrence and delivery; this is intentional. Exact duplicate deliveries never move either cutoff.
* Only a matching, still-pending password operation reserved **before** the evidence, for this principal/user/issuer/kind, can call 0008 `confirm_credential_change` under the same lock. Its internal receipt ID is the 0011 correlation UUID. Uncorrelated or superseded events leave pending operations quarantined. Factor logs never complete a factor reset, a 0010 approval, or controlled re-enrollment. `credential_operations` (not an `audit_events` lookup) is the authority for a pending password operation.
* Factor observations use 0009's governance fence and `record_client_totp_observation(..., source_time, NULL)`; newer independent observations prevail and a negative wins ties. No membership/status/role, minimum policy, activation, positive evidence or session privilege is issued here. Existing protected-route membership, client-operational, session and MFA checks remain necessary.

## Provisioning and external release gates (not performed)

1. Verify the authorized project, source transport and actual delivery semantics: immutable IDs, affected subject vs actor, completion vs attempt, operation correlation, clock ordering/precision, all credential paths, duplicates, replay/backfill, loss detection and retention. Stand up an authenticated private forwarder with a durable cursor/spool, lag alarms, rejection handling and key rotation/replay procedure. Do not use a dashboard screenshot, a public webhook, browser redirect, an `audit_events` row or a service-key fallback. No trigger on `auth.*`, hosted subscription, drain or provider configuration is installed here.
2. After separate infrastructure approval, create a dedicated unprivileged `bri_provider_ingest` LOGIN NOINHERIT with no ownership, inherited roles, role-management/DB-creation, replication, superuser or RLS-bypass powers. Require isolated network access and authenticated encrypted transport to the approved DB. Only the worker gets these credentials. Reject other memberships (except the non-inheritable, non-settable managed postgres admin edge checked by the runner convention). As restricted migration owner, pin the single approved issuer in `bri.provider_event_source`, grant **only** schema `USAGE` and `EXECUTE` on `bri.ingest_provider_security_event(text,uuid,uuid,text,text,timestamptz,uuid)`. Verify effective/default privileges and no indirect grants before use. Do not grant direct table access, `confirm_credential_change`, attestation, approval work, `SET ROLE`, or bootstrap credentials. The migration itself creates no login, secret, registry row or runtime grant.
3. **Delivery is not synchronous revocation.** Before hosted access, demonstrate that changes are pre-quarantined or checked against synchronous authoritative state on protected access, including source outages and replay gaps. An unpublished/delayed event cannot be enforced by this consumer. Define and verify how the access gate closes on a broken feed, restores only after reconciliation, and verifies controlled re-enrollment. No hosted access or recovery is certified by the local tests.

## Local verification

Run `PYTHONPATH=src:. BRI_TEST_PG_BIN=/path/to/pg16/bin python -m unittest discover -s tests -p 'test_provider_security_events*.py' -v` in the project venv, with inherited libpq settings removed. Without that opt-in only the adapter tests run. The integration tests initialize their own private Unix-socket cluster with no TCP listener, apply and recheck the real migration ledger as `bri_migrator`, and exercise the separate app and ingest logins. They sign synthetic input, not simulated provider output. No DSN, environment file, provider service, or persistent database is needed.
