# A11.5 ordinary-account deactivation

The owner approved this as a new subdivision of [A11](../planning/assignments-10-11.md#a115--ordinary-account-deactivation), not an originally numbered milestone.

- **Deactivation is not suspension.** It removes BRI access for an ordinary account and cannot be reversed through A11.3, provisioning completion, or delegated grant operations. Future restoration requires a separately authorized provisioning process; it must not reactivate historical grants by changing status alone.
- **Deactivation is not deletion.** Preserve the principal, underlying identity binding, membership history, business records, provenance and immutable audit. No provider operation, deletion request or erasure occurs.
- **Authority and evidence.** Only an active same-tenant client Admin with the explicit tenant-root `user:deactivate` permission and provider-verified TOTP from the past 15 minutes can act. Self, Admin and platform targets are excluded. Active ordinary accounts and ordinary A11.3 administrative suspensions qualify; pending accounts, external suspensions, deletion requests and credential holds do not. Submit an expected revision and one of `account_closed`, `access_review` or `policy_violation`, not free-form personal data. Preserve the two-eligible-admin rule and forced tenant RLS.
- **Commit boundary.** Migration `0022_user_account_deactivation.sql` reuses the lifecycle revision, A10 governance and session invalidation, and A11.4 delegated-grant ownership. It marks both the principal and membership deactivated, retires native active assignments as revoked, reconciles delegated grant state and advances its revisions, invalidates BRI sessions, and appends immutable audit in the same transaction. Any failure rolls all of it back. Terminal guards block ordinary restoration, new active grants and reactivation of historical grants. Existing suspension continues to have its original reversible behavior.
- **Review follow-up.** Migration `0023_deactivation_active_root_guard.sql` limits the deactivation-specific topology check to active assignments. Revoked rows still reference their nodes, and foreign keys, tenant isolation and other topology controls remain unchanged. The staged UI compares canonical decimal revisions without rounding: mutation acknowledgements must advance the revision, and a read at the same revision can only revalidate the identical state.
- **Release boundary.** The normal API and hosted proxy must not execute the action. The release migration must not grant routine execution to the hosted runtime role. Only isolated disposable fixtures may activate the database routine, after checking the default ACL. Provider assurance in the isolated app is exercised with an injected verification fixture, not a live provider.
