# A11.6 ordinary-account administration history

A11.6 is a new subdivision of the [approved A11 brief](../planning/assignments-10-11.md). History is read-only. It is not a new account mutation, a general audit viewer, an MFA-recovery workflow, or part of Data Disposition governance.

- The reader must be a currently authorized same-tenant client Admin. The existing directory authorization and target visibility still apply; the additional explicit `account:history:read` permission is independent of directory or general audit access. Deactivation does not hide the account's history. Foreign, excluded and nonexistent targets remain indistinguishable.
- The feed projects existing committed events only: provisioning requested, activated, display name changed, suspended, reactivated, permission granted/revoked and deactivated. Provisioning requested is not activation. No historical events are synthesized. The projection releases event ID, timestamp, action, outcome and a bounded recorded reason code, not a raw audit record.
- Actor identity is a separate visibility decision. An actor independently visible as an ordinary account in the same directory can be identified by BRI account ID and current directory display name. Unavailable actors use the neutral `Restricted actor` label without an identifier. No provider identities, correlation IDs, credentials, MFA evidence, recovery details or free-text notes are in the contract.
- History uses a GET-only same-origin endpoint and must not be cached. Paginate newest first by the event timestamp and UUID tie-breaker; the cursor is a UUID of a disclosed event, resolved inside the same authorized target and allowlist on every request. A cursor is not authority. A visible account with only pre-workflow legacy events can have an empty feed. Each page is a fresh authorized read, not a frozen multi-page audit snapshot.
- The PostgreSQL query must preserve forced RLS and immutable audit history with no direct read grant on raw audit. No permissions are seeded. Existing hosted mutation denial, provider restrictions and the Data Disposition boundary remain unchanged.
