## Catalogue and authority

A tenant has one two-level catalogue. Stable category/classification IDs are separate from display labels, used only within the owning tenant, and never recycled. Explicit idempotent starter provisioning does not overwrite customer edits or reactivate retired entries. Customer maintenance may create classifications, rename or describe them and retire them without deleting history. There is no node-specific catalogue or inheritance. Selection is only for a live operation on the caller's exact authorized source node; the catalogue never projects source associations, usage counts, or node names. Historical exact-version metadata readers may resolve retired labels after the format-specific access checks.

Catalogue mutation requires an explicit `classification:catalogue:manage` grant at the designated root. Use the existing authoritative single-root convention in migrations 0024/0025 and 0029: `node_type='root'`, parent NULL, and no other parentless node in the tenant. Missing or ambiguous topology denies; no heuristic selection. Follow the existing governance fence and guard against topology edits promoting a scoped grant. A role name does not grant authority, and catalogue management confers no read, review, publication or access-maintenance authority. `knowledge:metadata:propose` and `knowledge:metadata:review` are separate exact-node grants for subsequent corrections. Provision synthetic grants explicitly in local fixtures; the approved delegation API stays unchanged. Grant provisioning is therefore a remaining prerequisite for complete customer self-service.

## Metadata and versioning

Typed metadata version 1: one primary class, up to eight distinct additional classes different from the primary, title (1–160 UTF-8 bytes), optional description (up to 2,048 bytes), responsible node bound to accepted source scope, and independent optional effective, review and expiry dates. Date fields do not mutate authority, publication, retention or disposition. Do not invent an authoritative classification for historical unclassified knowledge. Maintain immutable proposal input and append-only authoritative revisions; presentation may show current labels and retirement, while audit retains original identifiers and labels as applicable. Use tenant-qualified association constraints and separate format-specific joins. Metadata revisions do not change source versions, bytes, digests, extraction or original provenance.

## Transaction boundaries and compatibility

Versioned request and response surfaces keep current strict CSV and XLSX contracts intact. Keep CSV protected submission without adding a unified upload screen. Bind immutable proposed metadata to each independently governed job at reservation. A submission retry with changed metadata must conflict rather than mutate the earlier proposal. Initial validation is part of the existing approval transaction, not a second queue. Every legacy callable approval path must fail closed for a metadata-bearing job lacking validated metadata in that transaction; existing unclassified approvals and accepted rejection behavior stay intact. Keep native independence including uploader and actual creator, replay/terminal conflict guarantees, lock ordering and atomic audit. A mismatch, failed decision, failed audit or failed validation rolls back the whole approval. A correction uses exact existing record/version, current-revision compare-and-swap, fresh exact permission plus exact-version access, proposer/reviewer separation and preserved original independence. Format-specific publication and both read gates remain authoritative. No classification operation writes to those gates.

## Future compatibility

An independently versioned future Intelligence Profile may specify stable class IDs, governing scope, validated metadata and explicit temporal predicates. It must intersect with live exact-version access and can never enlarge it. Ownership is hybrid: BRS standard templates, customer-controlled variants, optionally and explicitly delegated department variants, and mandatory non-overridable platform controls. No registry, selector, retrieval engine, AI, or changes to A13/A15/A18 behavior are part of A19.1.
