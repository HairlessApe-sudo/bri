# Independent Development Boundary

Status: Binding working constraints taken from the initiating brief; not a legal conclusion

## Purpose

BRI — Organisational Intelligence Infrastructure is a new independent product initiative with an independently authored specification, architecture, data model, implementation decisions and (only after authorization) source code. It is not a continuation, migration or refactoring of the previous BRI application.

## Permitted work in this stage

- The current BRI Municipal Foundation Build assignment explicitly authorizes local implementation in this workspace using synthetic data, plus tests and supporting documentation. This authorization supersedes earlier foundation-stage statements that implementation had not yet been authorized, but does not authorize production deployment, real customer/municipal data, production credentials, external services or disputed historical materials.
- Author new product, architecture, governance and planning documents in this project workspace.
- Use the initiating brief as the product-direction source.
- Use only the prior assessment reports expressly supplied/permitted as architectural lessons; they are not implementation specifications or authority to copy disputed material.
- Use synthetic examples and test data.
- Record risks and unresolved ownership, licensing, confidentiality and reuse questions for specialist legal review.

## Prohibited without separate explicit authorization

- Do not inspect, access, copy, import, adapt or reuse previous BRI source code, municipal implementations, or historical reports/materials unless a specific item is separately cleared for this assignment after provenance and rights review.
- Reuse unauthorized historical deliverables or proprietary materials.
- Access credentials, customer production accounts, external production services or real case data.
- Modify existing BRS production projects or existing files outside this new workspace.
- Install software, change environment/configuration, initialize a database, provision services, or create application source code/migrations.
- Begin implementation or deployment.

## Workspace rules

- All new project deliverables belong under this new project workspace.
- Do not overwrite/reorganize existing files; discover and preserve any pre-existing workspace content before writing.
- Keep prior reports reference-only and separate; do not copy their text wholesale into the new specification.
- Mark each statement as user-provided baseline, proposed, assumption, approved or unresolved where material.
- Stop and record a governance question if provenance or permission for a source is unclear.

## Change and authorization control

Before implementation, obtain explicit authorization stating permitted scope, target workspace, data/test constraints and allowed tools/actions. Each material product/architecture change must be logged with requirement impact, rationale, alternatives, owner and approval status. Silence or prior technical suggestions are not approval.

## Limitation

These technical controls do not establish legal ownership, clean-room sufficiency, license compatibility, confidentiality rights or freedom to operate. Specialist legal review is required before reliance on any disputed material or external dependency.
